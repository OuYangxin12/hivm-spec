# M4：符号档与候选性质

> 前置：M3 已完成（T3.0–T3.7 全部合入，390 passed / 2 skipped，六门禁全绿）。
> 本卡与 M1/M2/M3 卡同一纪律：**开工前定稿，改动走 PR，本地合并禁止**。

## 0. 这一程要解决什么

M3 交付了**具体执行档**：给定一组具体输入，两份 IR 跑出来的中间值逐 op 比对。
它的结论形式是"**在这组输入上**没发现发散"。

M4 要把结论提升为"**在有界范围内的所有输入上**没发现发散"。这是从"测试"到
"验证"的跨越，也是 FR1 真正意义上的兑现。

同时，M3 实测暴露了具体档的两条硬边界（见 M3 卡 §8.4），符号档恰好能部分绕开：

| M3 的阻断 | 影响面 | M4 的出路 |
|---|---|---|
| 逃生舱 op `mmadL1` 无具体值语义 | 20/41 语料整链失去可比性 | 符号档比**结构等价**，不需要具体值——`mmad(a,b)` 作为未解释函数（uninterpreted function）两侧一致即可 |
| 动态 shape 入参不猜具体值 | 20/41 语料 | 符号 shape，或用户显式提示 |

**但必须先说清楚 M4 不承诺什么**：符号档不会让 41 份语料全变 OK。受限子集
（D4/OD6）是**设计约束**而非临时偷懒，子集外的 op 仍然如实报缺口。

## 4. 设计要点（开工前约定，防走样）

1. **符号档不替代具体档，二者结论并列**。UNSAT（有界内无反例）与"具体输入上
   一致"是不同强度的结论，报告必须分别标注，不得混为一谈。

2. **未解释函数是逃生舱 op 的正解，不是万金油**。`mmadL1` 两侧都建模成同一个
   未解释函数 `f(a,b)`，则"两侧都调用 `f` 且实参相同"可判等价——但这**只能证明
   两侧做了相同的事，不能证明那件事是对的**。报告措辞必须区分这两者。

3. **受限子集之外必须报缺口，不得偷偷放行**。`SYMBOLIC_OPS` 是封闭集合，超出
   即报错（T3.1 已如此）。M4 不放松这条。

4. **z3 求解超时按缺口处理，不按通过处理**。超时的含义是"没证出来"，不是
   "证明了没问题"（FR6）。必须有显式超时上限并在结论中回显。

5. **poison 填充不得与合法值冲突**。未初始化读检查依赖"读到 poison = 读了未初始
   化内存"，故 poison 值不能是可能合法出现的数值（NaN 也不安全——真实计算会产生
   NaN）。需要独立的 tainted 标记位而非魔数。

6. **T4.4 是账本级快速检查，不做时序模拟**。它与 M2 的 timeline 工具**互补**：
   timeline 做交错探索（重），T4.4 做静态配对计数（轻）。二者结论不一致时以
   timeline 为准，且必须暴露不一致本身。

7. **有界范围必须显式声明并进结论**。"有界内无反例"里的"界"是结论的一部分，
   缺了它读者会误读为无条件成立——与 M2 截断语义同理。

### 8.3 两次自我纠错（本程最有价值的部分）

**其一：符号档的 false pass。** 首版在全语料上报 21 OK / 20 gap，远好于具体档
的 5 OK，一度以为是符号档绕开了动态 shape 与逃生舱的胜利。反向验证（对报 OK
的文件注入 `vadd→vmul`，看是否报 MISMATCH）发现两份注入后仍报 OK。深挖
`cv-pipelining-sec01-test_pipeline.mlir`：28 步里只有 2 步真的可比，其余因
`mmadL1` 逃生舱断链而没有值，注入的 `vmul` 恰好落在没比较的 26 步里。

具体档 `equivalence.py` 早有"覆盖缺口先行"这道防线（第 158 行），符号路径漏抄
了。补齐后符号档回落到 5 OK / 36 gap，与具体档一致——这才是真实水平。

**教训**：一个比对照组"好看很多"的数字，第一反应应当是怀疑而不是庆祝。反向
注入验证（"报 OK 的，注入缺陷后必须报 MISMATCH"）应当是每个新检查的标准动作。

**其二：崩溃当结论。** T4.5 压测发现表达式树深约 600 层时翻译器抛
`RecursionError`，整个工具带栈回溯退出。深展开的循环真会产生这种深度。已捕获
为 `UNKNOWN` → `COVERAGE_GAP`，附"可减小 `--bound` 后重试"。

### 8.4 性能

D10 新增三行，全部实测（详见框架 §10）。符号档 0.050s 最大单例，余量 ~6000×。

**一处必须说明的横比陷阱**：符号档（0.050s）比具体档（0.23s）快，**不是因为它
更强**，而是它不生成、不搬运具体张量。两档工作量不同，数字不可直接横比。

### 8.5 遗留移交

1. **符号档的覆盖面受限于逃生舱，与具体档同因**：36/41 报 gap 的主因是
   `mmadL1`/`nd2nz` 等无可执行值语义。符号档**没有**如 §0 设想那样绕开这个
   限制——UF 能让求解继续，但值链一旦断裂，后续步骤根本没有值可比。这是
   对 §0 预期的一次向下修正，如实记录。
2. **Real 语义不覆盖浮点精度**：符号档报 UNSAT 不代表 f32 下无发散。浮点精度
   问题仍由 M3 具体档 + 容差负责。二者结论并列输出。
3. **递归上限 ~600 层**是当前翻译器的硬边界（已优雅降级，未提高上限）。若将来
   需要更深展开，应改为显式栈的迭代式遍历，而非调 `setrecursionlimit`。
4. `exp` 之外的超越函数若进入子集，需同步 `_UNINTERPRETED` 与 z3 翻译。

## 9. 语义决策

1. **z3 为可选依赖**（`[symbolic]` extra），理由是必要性而非体积：CI 四个 job
   里三个不碰符号后端。缺失时报 `COVERAGE_GAP` / 退出码 3，绝不静默跳过。
2. **`z3-solver~=4.15` → `>=4.15`**：实测 `~=4.15` 等价于 `>=4.15,==4.*`，会把
   z3 锁死在 4.x（当前最新 5.1.0）。该 extra 自 M0 预留后从未被安装，故错误一直
   未暴露——**预留的依赖声明必须在首次使用时复核**。
3. **`Verdict` 不新增 `PENDING` 成员**：PENDING 是退出码层概念
   （`EXIT_PENDING=3`），verdict 层用 `COVERAGE_GAP`。两层不混淆。
4. **符号数值语义用 Real 而非 FP**：FP 精确但非线性约束常超时。选 Real 是因为
   M4 定位于结构等价，数值等价归 M3。代价（不覆盖浮点舍入与结合律缺失）随结论
   输出，并有测试把边界钉死。
5. **`exp` 用未解释函数**：只保证同实参必同值。测试同时断言其反面
   （`exp(x) <= 0` 是 SAT），把"只能证明两侧做了相同的事"机器化。
6. **除法披露而非约束掉**：不自动加 `b != 0`——那会把"可能除零"悄悄改成"假设
   不会"，等于篡改被验证的语义。
7. **T4.3 用 tainted 标记位而非 poison 魔数**（偏离计划原文，已在 milestone-plan
   §6 记录）：魔数可能是合法计算结果，NaN 与真实计算产生的 NaN 无法区分。污染
   状态必须与数值分离。有测试断言实现中不出现魔数字面量。
8. **T4.3 的保守方向**：未建模 op 假定它写了（避免"描述没建模"把合法代码报成
   缺陷），条件写不视为已初始化。保守放行**必须留痕**，`tracked_buffers == 0`
   报 gap 而非 OK。
9. **T4.4 是账本级检查，与 timeline 互补而非替代**：冲突时以 timeline 为准，但
   冲突本身必须浮现。severity 分级（unpaired-wait 为 error，orphan-set 为
   warning）依据实测 37 warning : 1 error 的分布。
10. **符号名按位置派生**（`in0`/`in1`）而非 SSA 文本：两份 IR 的 SSA 名可能不同，
    用它做符号名会让两侧变成不同自由变量，判定恒能找到"反例"。

## 10. 核心命题复盘（§7.5 要求的明确答案）

> 问题：四程下来，「DSL 描述 → 配置文档 → 工具装配」是否真的做到了
> **新增正确性类别不改引擎**？

**答案：分两种情况，必须分开回答——笼统说"做到了"是不诚实的。**

### 10.1 新增一个 op：真的零引擎改动 ✅

M4 收尾时重做了 vdiv 实验，这次覆盖**全部五个工具**（含 M4 新增的两个检查与
符号档）。在 `specs/toy.py` 里加 7 行描述、不碰任何引擎源码：

```
$ python -m hivm_spec gen specs/toy.py specs/cv.py -o /tmp/config_vdiv.json
覆盖：19 个 op（逃生舱 1）
$ git status --porcelain src/ | wc -l
0                    ← 引擎源码零改动

$ for tool in ub_occupancy timeline sync_pairing uninit_read equivalence; …
ub_occupancy   OK
timeline       COVERAGE_GAP
sync_pairing   COVERAGE_GAP
uninit_read    OK
equiv(具体)     MISMATCH   首个发散：hivm.hir.vdiv@i0
equiv(符号)     MISMATCH   反例 in0=0（求解器真的解了除法）
```

一个引擎从未见过的 op，五个工具**全部**即刻可用，符号档甚至解出了它的除法
语义。这条命题在 op 维度上成立，且 M4 新增的两个检查与符号档**自动继承**了
它——写它们时没有人为 vdiv 做过任何事。

### 10.2 新增一个正确性**类别**：需要改引擎 ⚠️

但 M4 新增的两个检查本身（`sync_pairing`/`uninit_read`）**各自都动了 5 个源
文件**：新引擎模块 1 个 + 四处封闭集合（`spec.py::KNOWN_CHECKS`、
`generate.py` schema enum、`__main__.py::_IMPLEMENTED_TOOLS`、
`assemble.py::_TOOLS`）+ CLI 帮助。

所以准确的表述是：

| 维度 | 是否需要改引擎 | 证据 |
|---|---|---|
| 新增 op / 新语义组合 | **否** | vdiv 实验，五工具零改动 |
| 新增正确性类别（新检查） | **是**，1 新模块 + 4 处登记 | PR #23/#24 各 5 文件 |

### 10.3 这是设计缺陷吗？不是，但要如实说

那四处封闭集合是**有意的**：schema enum 拒绝未登记的 check（T4.3 实施时它确实
拦了我一次），`_IMPLEMENTED_TOOLS` 让未实现的工具报 PENDING 而非静默。它们是
FR6/FR7 的落点——代价是加新检查要在四处登记，收益是不可能出现"配置里写了个
工具、跑起来却什么都没做"。

而 AGENTS.md §3.5 的原话本就是**"扩语义靠写描述"**，不是"扩一切靠写描述"。
新增正确性类别属于扩**引擎能力**，本就在 §3.5 划定的"扩基元"路径上。

### 10.4 结论

命题成立，但其适用范围应当被精确表述为：

> **新增 op、新语义组合、新算子变体 → 写描述，不改引擎**（已四程验证）；
> **新增正确性类别 → 加一个引擎模块 + 四处封闭集合登记**（有意的设计，
> 因为封闭集合是防自欺的机械保障）。

前者是日常高频操作（HIVM 有上百个 op），后者是低频架构演进（四程共 5 类
检查）。把高频操作的成本压到"写几行描述"，正是这个架构的价值所在。

**遗留建议**：若未来正确性类别显著增多，那四处登记可以收敛成单一注册表
（一处声明、其余派生）。但在只有 5 类检查时引入注册表机制是过度设计，
现在不做。
