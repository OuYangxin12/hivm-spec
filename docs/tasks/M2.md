## 4. 设计要点（开工前约定，防走样）

1. **D6 复用遍历核**：T2.1 与 T3.2 共用一个遍历核心；核心层不得 import `bishengir`。
   时序引擎消费 `VModule`（含 `VSync`），与占用引擎平级——**不许**为时序另写一条
   MLIR 遍历。
2. **结构判定与观测分离**（T2.3 vs T2.1/T2.2）：结构性死锁（wait 引用的事件无人
   set、或 wait-for 图成环）是**不依赖策略探索的确定性结论**，必须与"探索策略下
   未发现"严格分层输出，后者永远带策略集限定语。
3. **展开界的诚实口径**：循环 trip 未知时按展开界截断，结论必须携带"截断"限定；
   静态 trip（如 preload 的 `c4`）不截断。
4. **计数配平 ≠ 顺序可行**：L0 语料 `waits_before_sets_deadlock` 是本项目的立论
   案例之一（FileCheck 必然漏过）。T2.3 的最小验收就是它。
5. **multi_buffer 与时序**：`hivm.multi_buffer=N` 意味着 buffer 的 N 个槽位在流水线
   上交替——时序图需按槽位区分，否则会出现虚假的 RAW 依赖。T2.4 渲染时处理。
6. **预算**：D10 表 timeline ≤30s/kernel；探索策略 × 展开界组合爆炸时先降展开界，
   不删策略（止损：删能力不可逆，降界可逆）。

## 5. 风险与止损

| 风险 | 触发信号 | 处置 |
|---|---|---|
| VIR 缺时序所需信息（如 op 耗时模型） | T2.1 建模受阻 | M2 只做**事件序与依赖**，不做绝对耗时（耗时模型属 M3+）；甘特图用"事件步"而非时钟 |
| 策略组合爆炸 | 30s 预算超标 | 先降展开界（记入结论限定语），再砍策略；都救不了 → 上报（D1 复查条款） |
| `scope.scope`/嵌套 region 内同步语义不确定 | preload 家族 verdict 反常 | 以下游可见性最保守解释（scope 出口才可见），登记 D9 漂移，不得反推 |
| VIR 契约需扩展（如 VSync 增字段） | 破坏性变更 | 框架 §6.1 版本化条款：同步全部消费引擎 + 本卡记录变更理由 |
| **需上报决策** | ① 结论 schema 无法同时表达结构层与探索层；② cv kernel 存在引擎无法解释的真实同步形态；③ 预算需上调 | 停下，写清证据后交用户决策 |

### 8.3 性能记录

- 泳道前沿调度（每步候选 = 各泳道前沿）把模拟从 O(n²) 降到 O(n×泳道数)：

### 8.4 遗留与移交

- `effects=["write","read"]` 注解（cv 描述）对 timeline 无影响：时序模型只消费
  `vm.pipes` 与 VSync，不消费效应——已确认为设计内现象，非缺口。
- `hivm.multi_buffer=N` 的槽位交替在 M2 事件步模型下不产生虚假 RAW 依赖
  （模型没有逐 buffer 访问排序），渲染层暂不区分槽位；若 M3 耗时模型需要，
  再按设计要点 5 处理。
- L1 的 `sync-solver-round-robin-event-id.mlir` 中 30 处同步 op 全部位于
  `// DEFAULT:` 注释（调试打印 dump），非可执行 IR → vacuous 判定正确。
  真实 flag 形态的规模化验证待 M3+ 拿到带显式同步的真实 kernel dump。

## 9. 语义决策与漂移登记（D9 候选）

1. **flag 初态 = 已装载（re-arm 模型）**：`INITIAL_ARM=1`。依据：M1 卡"首个
   re-arm set"措辞隐含 flag 出厂即 armed，set 是"re-arm"；且初态已装载使等待
   更易放行，方向上压制假阳性死锁（NFR2）。同泳道 1:1 配平 + 初始装载 =
   自续握手（健康），2:1 起才饿死——测试 `test_same_lane_balanced_pair_with_rearm_is_healthy`
   锁定该口径。**已登记**：`spec.assume("timeline/flag-initial-state", ...)`（见
   `specs/toy.py`），风险方向 `false-negative`，销案时点 M3，信任已因此封顶
   provisional（账本 `frozen_by_assumption`）。**待主仓 C++ 链对拍确认初态语义。**
2. **泳道归属取具名属性**：`set_flag → set_pipe`、`wait_flag → wait_pipe`、
   `sync_block_* / pipe_barrier → 自身 pipe 属性`；正则首匹配会误取 tpipe
   （对端泳道），已修复并有回归。事件 id 取 `static_event_id / static_flag_id /
   flag` 属性或 `<EVENT_IDn>` 括号。
3. **set/wait 配对只按 event id，不依赖括号方向**（设计要点既定）；方向约定
   与初态语义同批对拍，若发现偏差按 D9 登记漂移。**已登记**：
   `spec.assume("timeline/pair-direction", ...)`，销案时点 M3。
4. **死锁诊断按 (rule, event_id) 去重**：同一缺陷在展开循环里复制成 N 个受阻
   步，报首现位置 + 受阻总数，既保 FR5 可定位又不淹没摘要。

## 10. 设计符合性审查与整改（2026-09-09 复审）

M2 标记完成后做了一次针对"是否偏离设计"的复审，查出 3 个问题并已全部整改。
记录在此以便 M3 起的判定能力演进有据可依。

### 10.1 发现 1（真实设计偏离）：确定性层跨泳道饥饿盲区

**症状**：跨泳道 2 wait : 1 set（生产者 set 在 PIPE_MTE2、消费者 wait 在
PIPE_V，16w:8s+1 初装）判为 `OK`/exit 0，而 7 个 wait 实际永久饿死。

**根因**：规则 A/B 都不覆盖该形态——事件有 set（A 不触发）、异道 set 永远可达
（B 的"set 全不可达"前提不成立）。而跨泳道恰是流水线握手的**常态**，
FR2 要求"判定是否存在无法推进的执行"，这是能力缺失而非口径选择。
更糟的是：7 个 wait 在**全部 7 个策略**下受阻集合完全一致（`[13,15,16,18,19,21,22]`），
工具明明已观测到这个不变量，却把它标注为"schedule 依赖观察"并输出
"未发现死锁"——诊断与自身证据矛盾（触碰 FR4/FR6 诚实性底线）。

**整改**：

1. 新增**规则 C（arm-deficit）**：展开域内 `waits > sets + INITIAL_ARM` 且
   **无截断** → 确定性 DEADLOCK。这是纯计数论证（供给 < 需求，任何调度都不能
   凭空造 arm），与交错顺序无关；截断时禁用（截断会削减 set 供给制造假短缺，
   与规则 B 同一 NFR2 保护）。诊断定位到**第一个必然饿死的 wait**
   （第 `sets+INITIAL_ARM+1` 次），而非首个 wait——前者才是问题所在。
2. 受阻观察分类 `classify_blocked`：全策略受阻集合一致 → `schedule-invariant`
   （新 rule `timeline/blocked-schedule-invariant`），随策略变化 →
   `schedule-dependent`。前者不再谎称"schedule 依赖"。
3. claim 自洽性：verdict 非 DEADLOCK 但存在 schedule-invariant 受阻时，
   claim 追加"但有 N 个 wait 在全部策略下均受阻……不可读作'无死锁'"。
4. 诊断按步骤聚合（原为 策略×步骤 笛卡尔展开，7×7=49 条同质 warning 淹没摘要），
   完整策略清单保留在 `extra.strategies`。
5. `details.arm_supply` 输出供需账目（无论是否触发判定）——账本本身即诊断材料。
6. 引擎版本 `0.1.0 → 0.2.0`：判定能力变更必须体现在审计坐标里。
7. 语料 +3：`crosslane_arm_deficit`（新盲区）、`crosslane_balanced_handshake`
   （规则 C 的**假阳性防线**，与前者仅差一次 set）、
   `balanced_misordered_same_lane`（计数配平但错序，此前无语料锁定该立论）。
8. 测试 22 → 28。其中 `test_strategy_blocked_is_warning_not_verdict` 原本
   断言 3w:1s 场景为 OK 并归为"schedule 依赖"，而它自己的 docstring 就写着
   "必有一个饿死"——病灶被固化进测试的实例，已按事实改判并拆成两个测试
   （`test_three_waiters_one_set_is_arm_deficit` + 供给充足的真·schedule 依赖场景）。

**遗留**：规则 C 只在**无截断**时可用。动态 trip（L2 常态：`%bound`/`%step`
为 func 参数）下截断即降级，跨泳道饥饿仍只能给 schedule-invariant 警告。
彻底解决需要"每迭代供需差"的归纳论证（trip 无关），列为 M3+ 候选。

### 10.2 发现 2（流程漂移）：本地合入使 CI 门禁结构性失效

**症状**：M2 及前一批整改都是本地 merge（未推送、无 PR），`origin/main` 落后
2 个 merge。milestone-plan §8 要求"CI 四门禁全绿方可合入"，但 feature 分支
没上过远端，CI **不可能**跑过——merge 与 feature 提交只隔 21 秒，本地预检也
无留痕。D5 声称的"机器门禁不可绕过"在这条路径上退化成口头纪律。

**整改**：新增 `scripts/merge_gate.py`——本地合入前置门禁，跑 CI 门禁的本地
等价物（lint/format/types/core-tests/corpus-manifest/spec-gate，spec-gate 的
base 取 merge-base 以免漏检未推送提交），结果落 `build/merge-gate.json` 作为
可审计证据（HEAD、时间、逐门禁结论、工作区是否干净）；工作区不干净即拒绝
（否则"绿"不对应任何一个提交）。`--check` 校验证据是否覆盖当前 HEAD。
条款写入 milestone-plan §8「本地合入例外」与 AGENTS.md §1。
**它不是 CI 的替代品**——推送后 CI 仍是权威。

### 10.3 发现 3（登记缺失）：最敏感的语义假设不在账本内

**症状**：`INITIAL_ARM=1`（flag 初态）是全模型最敏感的语义决策，若真实初态为
未装载，`wait-before-first-set` 的真实死锁会被放行（假阴性，与发现 1 同向叠加）。
但它只写在本卡 §9 的散文里：机器读不到、结论里不声明、不冻结 trust。
根因是 DSL **没有**假设登记 API——`DriftEntry` 结构存在但 `generate()` 从未
填充过它，D9 的账本机制实际是空转的。

**整改**：

- DSL 新增 `spec.assume(subject, assumed, authority=, rationale=,
  risk_direction=, resolve_by=)` 与 `SemanticAssumption`（D9 **前置**登记：
  漂移的前身是"猜了但还没对拍"）。重复登记同一 subject 报错——一个主体只能有
  一个当前假设，避免账本堆叠互相矛盾的历史猜测。
- 假设**进 spec_hash**：假设变更即语义口径变更，必须产生新 hash，否则历史
  结论无法与其前提对应。配置文档 schema 同步（`assumptions` 段）。
