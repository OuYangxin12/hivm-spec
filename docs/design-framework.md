# HIVM 语义验证：验证器生成器方案框架（草案 v0.1）

> **状态**：方案框架讨论稿。配套文档：`requirements.md`（需求基线，FR/NFR/AC 编号沿用）。
> **范围声明**：本文档给出组件划分、机制方向与里程碑骨架；标注【已定】的决策不再重复讨论，标注【待定】的条目汇总于 §10，属于后续讨论议程。语法细节一律以"示意"标注，不作为定稿。

---

## 1. 目标回顾

为 vibecoding 的 pass 开发提供快速语义验证：agent 能够在开发回路内获得 **success/fail 判定**与**运行状态视图**，据此快速失败并纠正方向。核心命题：**MLIR 千变万化，正确性类别有限**——因此不逐个建造验证工具，而是建设一个**验证器生成器**：agent 用 DSL 建模语义域，生成器产出面向特定正确性类别的 spec 工具。

## 2. 总体架构

```
                 ┌────────────────────────────────────────┐
  agent 写描述 ──►│ DSL 解释器 / 生成器（纯 Python，唯一重资产）│
                 │  · 描述静态检查(引用完备/一致性/覆盖)       │
                 │  · 归一化 → 配置文档                       │
                 │  · 元编程装配引擎 → spec 工具实例           │
                 └──────┬──────────────────┬───────────────┘
                        ▼                  ▼
             ┌─────────────────┐  ┌─────────────────────────┐
             │ spec 工具(生成物) │  │ spec 工具(生成物)         │
             │ 等价验证         │  │ 状态视图                  │
             │ MLIR×2 →        │  │ MLIR → 时序图/UB占用图    │
             │ success/fail    │  │ （本框架首批，见 §7）      │
             └─────────────────┘  └─────────────────────────┘
                  统一契约：吃 MLIR(+描述引用)，吐结构化结论/视图
```

| 组件 | 职责 | 期次 |
|---|---|---|
| DSL 描述库 | agent 编写的语义域描述（Python 模块），入库版本管理 | 随任务生长 |
| 解释器/生成器 | 加载、静态检查、归一化、产出配置文档、装配工具实例 | M0 起 |
| 固定引擎组 | IR 接口 / 状态机调度 / 值执行 / 视图渲染 / 结论框架 | 分期，§6 |
| 配置文档 | 描述的编译产物：可 diff、可评审、可缓存的规整化语义表 | M0 起 |
| 账本与绊线 | op↔描述覆盖状态、方言演进构建期检查 | M0 起骨架 |

## 3. 已定决策记录

### D1【已定】纯 Python 实现全栈
- **内容**：DSL 本体、解释器/生成器、固定引擎、spec 工具均为纯 Python。
- **理由**：vibecoding 主语言即 Python，agent 编写/消费零摩擦；描述、检查、生成、执行同语言，元编程路径最短；项目已有 Python bindings（`bishengir/python`，含 hivm/hfusion/hacc/annotation 方言绑定）可复用。
- **代价与复查条件**：数值执行与符号执行的吞吐受 Python 限制——首期以 numpy 向量化 + 小规模输入（缩小 tiling）满足 NFR1；若后续不达标，复查条件是"预算内跑不完典型 kernel"，届时仅替换引擎执行核，DSL 与生成器不动。

### D2【已定】生成物 = 配置文档 + 元编程装配，非独立二进制
- **内容**："生成 spec 工具"的含义是：解释器把描述归一化为**一份配置文档**（描述的编译产物），运行时由固定引擎按配置文档装配出工具实例；元编程用于把描述中的声明/函数转换为引擎可执行的对象（执行计划、双模可调用体、检查器参数）。
- **理由**：省去二进制 codegen 的构建链成本；配置文档可 diff、可评审、可缓存、可版本化，天然承载信任等级与 provenance；Python 元编程足以完成装配。
- **影响**：spec 工具的用户体验仍是"一个命令"（薄 CLI 包装：`spec-tool <name> <inputs>`），但其实现是"引擎 + 配置文档"。

### D3【已定】首批生成物 = 状态视图工具，从简单开始
- **内容**：首批工具为 **UB 占用图（M1）**与**时序图（M2）**；等价验证工具后置（M3 具体执行档，M4 符号档）。
- **理由**：状态视图不需要符号引擎与浮点语义（只消费尺寸/效应/调度），是全案中工程最薄、价值最即时的垂直切片；同时 `vm` 状态模型是等价工具的前置地基，先建它不产生返工；直接服务 preload/CV 类特性的高频问题（溢出、流水化失效）。
- **顺序依据**：UB 占用图只需顺序执行语义（无需并发调度），比时序图更简单，故 M1 先行。

### D4【已定】OD1–OD12 全部采纳
采纳结果摘要（业界依据与备选项见 `industry-research.md`）：
- OD1 双模值 → 方案 A：轻量符号句柄（受限表达式子集），z3 延后至 M4；
- OD2 调度口径 → 两层：wait-for 图确定性层（结构性死锁，确定性结论）+ 有界策略探索层（顺序/轮转/pipe 优先/K 随机种子），报告措辞模板"在{策略集}×{展开界}内未发现"；
- OD3 容差 → rtol+atol 全局+per-op 覆盖；round_mode 显式表达；f16/bf16 用 ml_dtypes；
- OD4 描述治理 → 贴方言放置 + CODEOWNERS + trust 升级必须附对拍证据；
- OD5 接线 → AGENTS.md 新增 spec-gate（精确命令 + 强制时机）；
- OD6 锚点 → 三级分层（变换前 IR / HFusion 源 / 硬件 golden）；符号等价限值语义子集（设计约束，非可选项）；
- OD7 双架构 → 单模型 + arch 差异段参数化；禁止两份全量描述；
- OD8 逃生舱 → 注册制 + 效应强制显式 + 信任封顶 provisional + 必配性质测试；
- OD9 schema → spec_version + JSON Schema 校验 + 往返 golden 测试；不兼容变更=大版本；
- OD10 性能 → 定位声明"调试保真优先于吞吐"；numpy 向量化 + 缩小 tiling；numba/Cython 仅 D1 复查触发后引入；
- OD11 模型验证 → 每 op 三类用例（canonical / 与 C++ 链对拍 / Hypothesis 性质），与信任等级绑定；
- OD12 首切片 → 双 kernel：VecAdd（bring-up）+ cv-pipelining.mlir（目标场景）。

### D5【已定】防自欺依赖机器门禁，而非评审自律
- **内容**：FR6 的防线由 CI 硬门禁承载，不依赖人工评审纪律。落地件：
  `.github/workflows/ci.yml` 四个 job（lint+types / core 测试矩阵 / schema 往返 golden /
  spec-gate）+ `scripts/spec_gate.py`。main 分支保护要求 CI 全绿方可合入；
  单人阶段免**人工**审批，但机器门禁不可绕过。
- **spec-gate 强制规则**：
  - **R1** 描述（`specs/`）变更 → 必须跑对拍集（`specs/cases/`）；T0.6 起"描述变更但无对拍用例"为硬失败；
  - **R2** trust 升级（provisional→cross-validated→anchored）→ 变更集内必须附带 `specs/cases/` 证据，否则拒绝合入；OD8 逃生舱条目封顶 provisional，升级一律拒绝；
  - **R3** 未实现阶段报 `PENDING(<任务号>)`，禁止静默跳过（与 `COVERAGE_GAP` 同哲学：缺口是合法结论，静默不是）。
- **理由**：审查指出原设计存在唯一的机制性空洞——描述、引擎、门禁三者均可由同一 AI agent 修改并自行合入（`milestone-plan.md` §8 单人阶段 PR 免审批），"被验证者操纵验证依据"的路径完全敞开。FR6 是本项目相对 lit/FileCheck 的核心差异化价值，其防线不能建立在自律之上。
- **代价**：CI 与门禁脚本本身成为需要看护的资产（故 `.github/`、`scripts/spec_gate.py`、`AGENTS.md` 在 CODEOWNERS 中与描述库同级看护——能放松门禁的人等于能绕过防自欺）。

### D6【已定】VIR：引擎间唯一数据契约
- **内容**：新增 **VIR（Verifier IR）**——IR 接口引擎的唯一输出、其余所有引擎的唯一输入（详见 §6.1）。占用/生存期引擎、状态机调度引擎、值执行引擎一律消费 VIR，**不得各自遍历 MLIR**。任务 T0.0 在 M0 内先行落地其数据结构与不变量。
- **理由**：审查识别出一条架构腐化路径——T2.1（M2 按 vm 段模拟 pipe/event）与 T3.2（M3 解释 scf 控制流）本质是同一遍历/解释核的两种实例化；若分期各写一套，M3 之后每个 op 语义修复都要改两处，**本项目立意消灭的"双源真理"将在自己内部重演**。契约先于实现是唯一低成本时机（M0）。
- **代价与复查条件**：M0 增加约 2 天契约设计成本；VIR 若在 M2 被证明表达力不足（如需表达推测执行），按 §6.1 版本化规则演进，但"单一遍历核"原则不放弃。

### D7【已定】双层 Python 版本策略：核心与 IR 接口层隔离
- **内容**：
  - **核心层**（DSL/生成器/状态机/占用/值执行/渲染/结论框架）：纯 Python，**不 import bishengir**，`requires-python = ">=3.10"`，CI 矩阵实测 3.10 + 3.12；
  - **IR 接口层**：依赖主仓 bindings（**cp310 ABI**），经 `extras[ir]` 声明，测试以 `requires_bindings` marker 隔离；
  - CI 与本地高版本环境跳过该 marker，但跳过必须渲染为**显式覆盖缺口报告**（`tests/conftest.py::pytest_terminal_summary`），不得表现为静默通过；IR 接口层的回归责任由编译服务器远端执行承担。
- **理由**：审查指出 `requires-python = ">=3.9"` 与现实脱节——绑定 .so 为 cp310，本地 venv 为 3.14，按声明装 3.9 必然踩坑。3.10 是 ABI 强制的地板而非偏好（`tests/test_packaging_baseline.py` 以测试守护该下界）。分层的额外收益：核心层测试不受稀缺绑定环境阻塞，CI 可在公共 runner 上跑绝大部分回归。
- **已知缺口（登记而非隐藏）**：IR 接口层在公共 CI 上无覆盖。缓解：远端执行 + 缺口报告可见性；若未来自托管 runner 可用，此缺口关闭。

### D8【已定】FR1 最小等价内核为不可裁剪交付项
- **内容**：`requirements.md` 将 FR1（语义等效）列为 P0，而里程碑将其排在 M3/M4。为对冲"只做完 M1/M2 即停"的风险，特此约定：
  - **最小等价内核** = 具体执行差分（固定种子输入）+ 逐 op 值哈希 trace + 首发散点定位，对应 T3.1/T3.2/T3.5/T3.6，**定义为项目不可裁剪的交付底线**；范围可缩（op 子集、静态 shape、单 kernel），但该能力不得整体删除或无限延期；
  - M1 的 VIR 与遍历核**必须为解释执行预留接口**（§6.1 值槽位与执行轨迹钩子），使 M3 是扩展而非重写；
  - 若 M3 触发延期，须在本节显式记录延期理由与新的兑现时点，而非默认顺延。
- **理由**：UB 占用图与时序图的价值定位是"调试辅助"，等价验证才是"防自欺判定"，直接对应最痛的缺口 G1。审查指出：若资源在 M2 后耗尽，项目将留下两个状态视图工具，而 P0 需求完全未兑现。业界参照支持该内核选择——EDA 常态是"LEC 限子集 + 仿真差分为主力"（OD6），差分执行正是主力手段。

### D9【已定】语义漂移：记账优先 + 主仓 C++ 链默认权威
- **内容**：当描述语义与主仓 C++ 链行为不一致时（详细流程见 §8.1）：
  1. 漂移**一律先登记** drift ledger 条目，并**冻结该 op 的 trust 升级**；
  2. **默认权威 = 主仓 C++ 链**（本项目是纯下游使用者，见 `milestone-plan.md` §8），即默认动作是修描述；
  3. **唯一可推翻默认的证据 = 硬件 golden**：经硬件锚定证明 C++ 链有 bug 时，描述保留己方语义、条目标注 `upstream-suspected`，并按主仓 AGENTS.md 规范准备补丁（不主动上游化的既定关系不变）；
  4. 漂移条目未闭环期间，涉及该 op 的结论强制降级标注。
- **理由**：审查指出原文档只写"漂移=bug 信号"而无处置流程与仲裁权归属。无预设规则时，agent 遇漂移会自行选择便利解释——这等于放大防自欺风险。选择 C++ 链而非 spec-first 是为与"纯下游使用者"的既定关系一致（spec-first 治理需要上游化通道，本项目明确不走）。

### D10【已定】NFR1 细化为 per-tool 预算并确认为基线
- **内容**：NFR1 的"建议值待确认"就此关闭，确认为下表基线（同步至 `requirements.md` §4.2）。每个里程碑退出时实测回填；超限即触发 D1 复查条款（仅替换执行核，不动 DSL/生成器）。

| 工具 | 预算 | 判据里程碑 | 实测 |
|---|---|---|---|
| UB 占用图 | ≤ 10s / kernel | M1 (T1.7) | **0.20s**（L2 目标 kernel 19 份，最大单 kernel；余量 51×） |
| 时序图 | ≤ 30s / kernel | M2 (T2.6) | — |
| 等价验证（具体档） | ≤ 5min / kernel 对 | M3 (T3.7) | — |
| 特性级完整验证 | ≤ 10min | M3 末 | — |

> **实测口径（T1.7 终版）**：19 份 L2 目标 kernel（cv-pipelining 18 分节 + preload，
> 收割自主仓 UT）逐份计时，单 kernel 最大 **0.20s**，19 份总计 3.25s。注意 0.2s 中
> 大部分仍是解释器与 bindings 加载开销，分析本身亚毫秒级——但这正是 M1 的设计点：
> 占用分析只消费尺寸与效应，本就不该慢。

- **理由**：原单一 30s 预算无法区分工具间量级差异——UB 占用图只消费尺寸与效应，与需要解释执行的等价验证不是同一数量级；粗粒度预算会掩盖轻量工具的性能退化，也使 M3.7（D1 唯一预设复查点）失去精确判据。

### D11【已定】DSL 语法定稿前置 3-op spike

> **✅ spike 已执行（T0.0b，`specs/spike_t0_0b.py`）**：逃生舱 **1/3**，未触发止损条件
> （≥2 即须重估 §4.4 并上报）。三 op 结论与由此导出的 T0.1 API 需求：
>
> | op | 结论 | 导出的 API 需求 |
> |---|---|---|
> | `vadd` | 可声明式 | `In[]`/`Out[]` 标注自动推导效应；`elementwise` 组合子 |
> | `set_flag`/`wait_flag` | 可声明式 | **独立 `sync_*` 效应原语**（不可用 rd/wr 硬套）；`Attr[]` 标注；`EventId`/`Pipe` 一等类型 |
> | `mmadL1` | 部分逃生舱 | `Variadic[]` + 数量约束；**`cond_wr` 条件效应**；`host_fn` 逃生舱（trust 自动封顶 provisional）|
>
> **关键发现**：② 暴露出"效应"不止内存读写——同步是对**同步状态**的读写。若 DSL 只有
> `rd/wr(space)` 一种原语，事件对根本无法表达。这正是 spike 要提前发现的表达力悬崖。
> ③ 的 `init_condition` 要求 `cond_wr`，否则条件语义在描述层静默丢失。

- **内容**：T0.1（Spec API 骨架）之前插入 **T0.0b 语法 spike**：用示意语法试写三个代表性 op——① `vadd`（平凡值语义）；② 跨迭代多 Wait/Set 事件对（效应复杂度，取自 `sync_related_args` 真实场景）；③ `mmad` 类（预期触发 OD8 逃生舱的布局代数）。三者均可表达（或明确落入逃生舱）后，API 方可定稿。
- **理由**：§4.2 语法明确标注"非定稿"，而 T0.1 直接实现 API。若第一版 API 仅由 toy 描述（alloc/load/vadd）驱动，将被最简单的 op 锁定；等遇到布局代数与跨迭代事件对时返工成本最高。spike 的产出同时是 OD8 逃生舱边界的第一份实证——**哪些 op 进不了声明式描述，应在写引擎前就知道**。

### D12【已定】工具契约限定为单 IR 输入，编排责任归 agent

- **内容**：spec 工具的输入契约**恒为"一份 MLIR + 描述引用"**（等价验证为两份：待验 IR + 锚点 IR）。工具明确**不做**以下事情：
  - 不接受 pass 序列 / stage 列表作为输入；
  - 不解析 `--mlir-print-ir-before-all` / `--print-ir-after=<pass>` 的转储集合；
  - 不在描述中建模 pass 顺序约束（如"GSS 必须先于 CreatePreload"）；
  - 不跨调用保持状态。

  **多 stage 定位（first bad pass）由 agent 编排**：agent 自行转储各 pass 的 IR，对每份分别调用工具，第一个出现异常 verdict 的 stage 即首恶 pass。

- **理由**：
  1. **与项目命题一致**。本项目赌的是"MLIR 千变万化，**正确性类别有限**"——收敛的是正确性类别。而 pass 数量、顺序、条件启用组合属于"千变万化"一侧，会随主仓 pipeline 持续演进；把它引入契约会使契约随上游膨胀，直接冲击 NFR4（不应随方言/流程演进而全量重建）。
  2. **不重复既有能力**。`--mlir-print-ir-before-all` / `--print-ir-after=<pass>` 是 MLIR 标准能力，主仓案例研究已将"转储并按 pass 切分"作为常规调试起手式；bisect 则是 agent 的原生强项。工具重新实现这两者属职责越界，且引入 dump 解析、stage 语义、bisect 策略等全新失败面。
  3. **可组合性**。单输入、无状态的契约使工具成为**可自由组合的原子操作**（Unix 管道哲学：做一件事并做好，编排留给调用者）。一旦工具自行理解 pass 序列，它便带有跨调用状态与假设，反而削弱 agent 编排它的自由度。而 agent 恰是本项目场景下最擅长编排的调用者——设计应当依赖这一优势，而非替它包办。

- **边界澄清**：等价验证接受两份 IR **不构成例外**。第二份是判定**锚点**（OD6 三级锚点分层），不是 stage 序列；其判定仍是"这一对 IR 是否等价"这**一个**正确性问题，符合单一职责。

- **被拒绝的备选**（留档以防重复提案）：
  | 备选 | 拒绝理由 |
  |---|---|
  | pass 序列扫描（工具吃 `--stage a.mlir --stage b.mlir ...` 并内建 bisect） | 重复 MLIR 转储能力与 agent bisect 能力；契约随 pipeline 膨胀 |
  | 描述中声明 pass 顺序不变量 | 表达力风险高，且与主仓真实 pipeline 极易漂移（放大 D9 的双源真理问题） |

- **来源**：该边界源于一次误判的纠正——审查者在 preload 死锁场景推演中曾将"工具无法指出 pass 顺序是根因"判定为设计缺口并提议 pass 序列扫描，经项目所有者纠正：工具应高度聚焦单个 IR 在受限语义环境下的快速分析，跨 pass 定位由 agent 用工具逐个获取分析数据完成。记录于 §13。

  2. **会让 VIR 契约被夹具细节污染**。为通过 189 个文件，VIR 将不得不容纳 unregistered op、单文件多模块重定义、占位 op——这些都不是 HIVM 语义，而是 lit 工程细节；契约一旦长出这些结构极难摘除（D6 的契约稳定性受损）。
  3. **长尾边际价值极低**。20 → 99 个 op 使覆盖率仅从 82.2% 升至 100%，建模量近 5 倍；而 M1 只需**效应级**建模（D3），80% 收益可极廉价获得。

## 4. DSL 设计方向

### 4.1 承载形态【方向，语法细节待定】
D1 之下默认倾向 **Python 内嵌 DSL**：描述即 Python 模块（dataclass/装饰器/fluent API 任选其一为骨架），可获得类型检查、补全、单测、import 组织等既有工具链，agent 无需学习新语法。独立文本 DSL 不排除，但需要论证其相对内嵌式的增量收益。

### 4.2 三段结构（概念示意，非定稿语法）

```python
# descriptions/hivm_membase_basic.py —— 示意
spec = Spec(arch="a3", version=1)

# --- ops 段：op 语义 = 值函数 + 效应 ---
@spec.op("hivm.hir.vadd", pipe=PIPE_V, effects=rd("a","b")+wr("out"))
def vadd(a, b, out): out[...] = a[...] + b[...]

@spec.op("hivm.hir.load", effects=rd(src.space)+wr(dst.space))
def load(src, dst): dst[...] = src[...]

# --- vm 段：状态模型 ---
spec.space("gm", capacity=None)
spec.space("ub", capacity=chip.a3.ub_size, align=chip.a3.ub_align)
spec.pipe(PIPE_V, PIPE_MTE2, PIPE_MTE3, PIPE_M, PIPE_FIX)
spec.event("EVENT_ID0".."EVENT_ID7")

# --- checks 段：要生成的工具与口径 ---
spec.check("ub_occupancy", spaces=["ub","cbuf"])
spec.check("timeline", scheduling=conservative_strategies(n=4))
```

- 社区方言（scf/arith/memref/tensor）的语义**不进描述**，由引擎内置（对齐"官方 interpreter 内置 builtin 方言"的惯例）；描述只负责 HIVM 特有 op 与 vm 状态。
- 描述覆盖不到的 op：不写即 `UNMODELED`，工具触发时输出 `COVERAGE_GAP`（FR4），禁止静默。

### 4.3 双模值设计【已定（OD1·方案 A）：轻量符号句柄，z3 后端延后至 M4】
op 值函数写一次，两种模式执行：**具体模式**（操作数是 numpy 数组，直接算）与**符号模式**（操作数是符号表达式句柄，构建表达式图，供 M4 符号等价使用）。这是"描述写一次、后端多样"的技术支点，也是 D2 元编程的主要用武之地（把普通 numpy 风格函数转为双模可调用体）。符号句柄仅覆盖受限表达式子集（算术/比较/select），与 §4.4 概念清单一致；API 细则在 M3 前置设计中定稿（见里程碑计划 T3.1）。

### 4.4 表达力边界与逃生舱
声明式描述优先；无法表达者（如 custom 内置库、复杂布局代数）走显式逃生舱（注册 host Python 函数），逃生舱条目在账本中单独标注信任状态（§10 OD8）。DSL 概念清单（§4.2 所列）之外的表达能力**一律不加**，防止 DSL 范围失控。

## 5. 生成器机制（D2 展开）

```
加载描述 → 静态检查 → 归一化 → 配置文档 → 元编程装配 → spec 工具实例
```

1. **静态检查**（生成前置门）：引用完备（op/space/event/pipe 均已定义）、值函数签名与效应声明一致、check 声明的空间存在、覆盖状态合法。不通过 → 拒绝生成并给出定位（FR4/FR7 在生成层的落点）。
2. **归一化**：把 Python 描述折叠为稳定顺序的规整化语义表（消除书写顺序/风格差异），保证同一描述产出逐字节稳定的配置文档（FR8）。
3. **配置文档**（schema 草案要点，版本化见 §10 OD9）：
```json
{ "spec_version": 1, "arch": "a3",
  "ops": { "hivm.hir.vadd": { "value_ref": "...", "effects": [...], "trust": "provisional", "provenance": {...} } },
  "vm": { "spaces": [...], "pipes": [...], "scheduling": {...} },
  "checks": [...], "coverage": { "modeled": [...], "unmodeled": [...] } }
```
4. **装配**：引擎按 checks 选择与配置文档构建工具实例；薄 CLI 提供统一入口。

## 6. 固定引擎组合

| 引擎 | 职责 | 依赖的描述段 | 期次 |
|---|---|---|---|
| IR 接口引擎 | 解析 MLIR 文本（Python bindings），抽取 op 序列/循环结构/alloc/sync 结构，产出 **VIR**（§6.1）；**唯一接触 bindings 的组件**（D7）。**强制 bootstrap 前置条款见下方** | — | M0 |
| 状态机调度引擎 | 按 vm 段模拟执行：pipe/event 状态推进、保守交错策略集、迭代展开（消费 VIR） | vm + ops 效应 | M2 |
| 值执行引擎 | 双模值的具体模式执行（numpy），沿 VIR 控制流解释（**不重写遍历核**，D6/D8） | ops 值函数 | M3 |
| 占用/生存期引擎 | alloc 生存期与 per-space 峰值统计（消费 VIR） | ops 效应 + vm 空间 | M1 |
| 视图渲染器 | 甘特式时序图、占用曲线：JSON（agent 消费）+ SVG/文本（人消费） | — | M1/M2 |
| 结论与诊断框架 | verdict 枚举（含 `COVERAGE_GAP`、`UNTRUSTED_DESCRIPTION`）、结构化诊断、描述哈希回写（`spec_hash` 定义见 §7.3） | 全部 | M0 |
| 账本与绊线 | 覆盖状态机（provisional→cross-validated→anchored）；方言新增 op 的构建期检查 | — | M0 骨架 |

> **IR 接口引擎强制前置条款（bindings bootstrap）**
> 主仓 bindings 存在注册缺口：`_mlir_libs` 站点初始化只探测 `_mlirRegisterEverything`，
> **不**探测带前缀的 `_bishengirRegisterEverything`，导致 hivm/hfusion/hacc 方言不会被自动注册。
> 因此 IR 接口引擎**必须**在 `ir.Context()` 创建后显式调用：
>
> ```python
> import bishengir._mlir_libs._bishengirRegisterEverything as _reg
> ctx = ir.Context(); _reg.register_dialects(ctx)   # MLIR 允许向活跃 Context 追加方言
> ```
>
> 该知识原仅存于 V1 探针脚本注释中，现提升为引擎显式条款：实现时须落为
> `hivm_spec.ir_interface.bootstrap` 模块并配 `requires_bindings` 回归测试（防止
> 绑定升级后静默回归为"方言未注册"）。另注意绑定 .so 为 cp310，版本策略见 D7。

### 6.1 VIR：引擎间唯一数据契约（D6，T0.0）

**规则**：IR 接口引擎是**唯一**接触 MLIR 与 bindings 的组件，产出 VIR；其余引擎只消费 VIR。
任何引擎绕过 VIR 直接遍历 MLIR 即为架构违规（M2 起由 lint/评审拦截：核心层禁止 import `bishengir`，见 D7）。

```
MLIR 文本 ──[IR 接口引擎]──► VIR ──┬──► 占用/生存期引擎 (M1)
   （唯一绑定接触面）                ├──► 状态机调度引擎 (M2)
                                    ├──► 值执行引擎     (M3/M4)
                                    └──► 视图渲染器
```

**结构要点（T0.0 定稿其字段与不变量）**：

| 元素 | 内容 | 消费者 |
|---|---|---|
| `VNode` | op 标识、源位置（MLIR Location）、操作数/结果引用、描述解析出的效应（rd/wr + space）、pipe 归属、**值槽位**（具体/符号模式的载体，D8 预留） | 全部 |
| `VRegion` / `VLoop` | 控制流结构：scf.for/if/while 的归一化表示，含迭代域（静态或参数化符号）、迭代参数与 yield 绑定 | M1 生存期、M2 展开、M3 解释 |
| `VAlloc` | alloc 点、地址空间、尺寸来源（静态 shape / 编译器标注 / 测试参数化，含 provenance） | M1 |
| `VSync` | set/wait/pipe_barrier/sync_block 事件语义节点，含事件 id 与配对候选 | M2 |
| `VTrace` 钩子 | 执行轨迹回调接口：逐节点值哈希、状态快照（**D8 要求的解释执行预留**） | M2/M3 诊断 |
| `coverage` | 未建模 op / 未识别结构清单 → 直接驱动 `COVERAGE_GAP`（FR4） | 结论框架 |

**不变量**：
1. VIR 构造后**不可变**（引擎不得原地改写；派生分析产出旁挂结构），保障 FR8 确定性与多策略并行探索的隔离；
2. 节点顺序为**确定性程序序**（同一 MLIR 输入逐字节稳定，与配置文档同一 FR8 口径）；
3. 每个 `VNode` 必须可回溯到 MLIR 源位置——FR5 可诊断性的物理基础；
4. 不认识的 op/结构**必须**落入 `coverage`，不得静默丢弃（FR4）。

**程序序的单一真源（T1.1 契约修订）**：`VRegion.items` 是**节点与子区域交错的单一序列**，
`nodes` / `regions` 退化为派生视图（`@property`）。

- **修订理由**：初版把两者分成 `nodes` 与 `regions` 两个元组，遍历约定为"先节点再子区域"。
  T1.1 用真实语料验证时发现，这会让循环**之后**的 `store` 排到循环**体内**的 `vadd` 之前
  （实测 `loop_load_add_store.mlir` 得出 `n4, n7, n6`，而源码行号为 10, 14, 12）。
- **为何必须修**：若 `wait` 在循环体内、`set` 在循环之后，错误的顺序会让 M2 得出**相反**的
  死锁结论——而"顺序而非计数"正是本项目相对 FileCheck 的核心价值（D6/§7.2）。
  两个分离的容器无法表达相对位置，属结构性缺陷，非实现 bug。
- **回归防线**：`test_program_order_interleaves_nodes_and_subregions`（手写 VIR）+
  `test_program_order_matches_source_line_order_on_real_ir`（真实 IR 上断言行号递增）。

**空洞结论的防线（T1.4 实测补强）**：工具**不得**在"未分析到任何对象"时给出 `OK`。

实测 `annotate-vf-alias.mlir` 曾拿到干净的 `OK`——该 kernel 的 3 个 UB buffer
是 `func.func` 参数而非 `memref.alloc`，引擎一个都没捕获，占用被算作 0。
"安全"与"无知"的外观完全相同，这是本框架最该防的假阴性。故：

| 情形 | 判定 |
|---|---|
| 被检查的 space 中零 buffer | `COVERAGE_GAP`，且明说"不代表不溢出，而代表未能分析" |
| buffer 尺寸未知 | 计入缺口；峰值仅为**下界** |
| 容量未知 | `COVERAGE_GAP`（不可拿"不知道"换"没问题"） |
| 片上 buffer 来源 | 区分 `LOCAL_ALLOC` 与 `FUNC_ARG`；后者生存期覆盖全函数 |

**版本化**：VIR 为内部契约，不承诺对外稳定；但破坏性变更须同步更新全部消费引擎，且在本节记录变更理由（避免退化为各引擎私有分支）。

### 6.2 bindings 获取与本地可用性（T1.1 实测）

绑定树可整体拉取到本地供开发使用，`scripts/setup_bindings.sh` 已固化该流程。

| 事项 | 实测结论 |
|---|---|
| ABI | `cp310`——**必须** CPython 3.10；更高版本无法加载 `.so` |
| 体积 | 约 246M（84 个文件 + **139 个符号链接**） |
| 关键陷阱 | 树内符号链接指向构建目录，`rsync -az` 会得到 139 个**悬空链接**且无报错；必须用 **`rsync -azL`** 解引用 |
| 方言注册 | 站点初始化**不会**自动注册 hivm，须显式调用 `_bishengirRegisterEverything.register_dialects(ctx)`（框架 §6 强制条款） |
| 定位方式 | `HIVM_SPEC_BINDINGS` 环境变量，回退 `/tmp/bindings` |

**探测逻辑只有一份**：`tests/conftest.py` 委托 `hivm_spec.bindings.bindings_available()`，
不自行判断。两处独立探测必然漂移，会造成"conftest 跳过而引擎其实能加载"的错位；
且绑定树不在 `sys.path` 上，`find_spec("bishengir")` 判不出来。


## 7. 首批 spec 工具规格

> **输入契约（D12）**：每个工具恒吃**一份** MLIR + 描述引用；等价验证吃两份
> （待验 IR + 锚点 IR，后者为 OD6 锚点而非 stage 序列）。锚点需求按检查类别区分：
>
> | 检查 | 需要锚点 IR | 原因 |
> |---|---|---|
> | UB 占用图（§7.1） | ❌ | 溢出是待验 IR 的**内在性质**，对照的是硬件容量线 |
> | 时序图/死锁（§7.2） | ❌ | 死锁是待验 IR 同步结构的**内在性质** |
> | 等价验证（M3） | ✅ | "变换是否改变计算结果"必须有参照物（默认锚点=变换前 IR） |

### 7.1 工具一：UB 占用图（M1）
- **输入**：目标 MLIR + 描述引用 + 架构配置（A3/A5）。
- **行为**：沿 IR 顺序语义计算各 `memref.alloc`（按地址空间）的生存期，输出 per-space 占用曲线与峰值，对照容量线；超限给出贡献者排序（alloc 名、尺寸、活跃区间）。
- **输出**：JSON 曲线数据 + 占用图。
- **已声明的简化口径**：采用编译器标注的 buffer 尺寸（`inferAndSetBufferSize` 等若存在），同时输出"内在最小峰值"作对照；判定边界随输出附带（Q2 钩子）。

### 7.2 工具二：时序图（M2）
- **输入**：同上 + 调度策略参数。
- **行为**：按 vm 段模拟 pipe/event 状态推进，输出 iteration × pipe 的甘特式时间线、wait/set 依赖链标注；多调度策略分别呈现。
- **价值场景**：CV/preload 类特性——两 pipe 从不重叠（流水化失效）、wait 无可满足 set（死锁风险）在图上直接可读。
- **已声明的简化口径**：保守交错策略集 + 有界迭代展开（参数进 §10 OD2）。

### 7.3 统一输出契约
```json
{ "tool": "ub_occupancy", "verdict": "OVERFLOW|OK|COVERAGE_GAP|UNTRUSTED_DESCRIPTION",
  "spec_hash": "...", "engine_version": "...", "trust": "provisional",
  "details": {...}, "diagnostics": [...] }
```
verdict 为封闭枚举；`COVERAGE_GAP`/`UNTRUSTED_DESCRIPTION` 是合法结论而非错误（FR4/FR7）。

**`spec_hash` 定义（消除审计链歧义）**：

```
spec_hash = sha256(归一化配置文档的规范字节串)
```

- **哈希对象是配置文档而非描述源文件**：归一化已消除书写顺序与风格差异（§5.2），
  故配置文档是语义的规范表示——源文件的无语义改动（注释、格式）不应改变结论指纹，
  而任何语义改动必然改变它；
- **引擎版本单独成字段**（`engine_version`），不混入 `spec_hash`：语义与实现需可独立追溯，
  否则"引擎升级"与"语义篡改"在审计上无法区分；
- 复现一个历史结论所需的完整坐标 = `spec_hash` + `engine_version` + 输入 MLIR 哈希。

## 8. 信任与验证工作流

- **信任等级**：`provisional`（仅静态检查通过）→ `cross-validated`（与既有实现/分析对拍一致：C++ 链 41 op、GSS、PlanMemory）→ `anchored`（硬件 golden 锚定）。结论携带所用描述的**最低**等级。
- **防自欺（FR6 的 DSL 形态）**：描述进 git，语义篡改=显式 diff；spec 哈希写入结论，可复现可审计；未达 cross-validated 的描述产出的失败结论自动降级标注。**机制载体见 D5**（spec-gate 硬门禁；R2 强制 trust 升级附证据）。
- **模型自身的验证工作流**：对拍用例与描述同库存放（§10 OD11）；新增/修改描述必须跑对拍集（spec-gate R1 强制）。

### 8.1 语义漂移处置流程（D9）

**触发**：对拍失败、或 spec 工具结论与主仓 C++ 链/GSS/PlanMemory 行为不一致。

```
发现不一致
   │
   ├─(1) 登记 drift ledger 条目（必做，先于任何修复）
   │      字段：op、现象、复现输入、双方行为、发现时间、状态
   │      副作用：该 op 的 trust 升级冻结；相关结论强制降级标注
   │
   ├─(2) 归属判定
   │      ├── 描述错（默认）─────────► 修描述 + 补对拍用例 → 条目闭环
   │      ├── 主仓 C++ 链疑似有 bug ─► 需硬件 golden 证据（见 3）
   │      └── 硬件勘误/文档缺失 ────► 条目标 `spec-unclear`，描述取保守语义
   │                                    并在结论中声明该保守性
   │
   └─(3) 硬件 golden 仲裁（唯一可推翻"C++ 链权威"的路径）
          经真机取 golden → 若证明 C++ 链有误：
            · 描述保留己方语义，条目标 `upstream-suspected`
            · 按主仓 AGENTS.md 规范准备补丁备查（不主动上游化，既定关系不变）
            · 该 op 可升 `anchored`（有硬件证据）
```

**默认权威 = 主仓 C++ 链**。理由见 D9：本项目是纯下游使用者，且无预设规则时 agent 会自选便利解释，等于放大防自欺风险。

**硬件 golden 锚定流程（与 NFR3 的兼容口径）**：NFR3 约束的是**验证回路**不依赖硬件，
而非项目永不接触硬件。因此锚定是**离线、稀疏、人工触发**的独立活动：

| 项 | 口径 |
|---|---|
| 时机 | 仅在 ① trust 升 `anchored`、② 漂移仲裁需推翻 C++ 链 两种情况下触发 |
| 频率 | 稀疏（按需），不进开发回路、不进 CI |
| 产物 | golden 输入/输出对存入 `specs/cases/`，标注硬件环境与 CANN 版本 provenance |
| 回路影响 | 零——回路只消费已落盘的 golden 数据，不调用硬件（NFR3 保持成立） |

### 14.2 manifest 契约

每份非 L0 语料必须有一条记录；L0 记 `origin: "handwritten"`。

```json
{
  "schema_version": 1,
  "entries": [
    {
      "path": "l1/sync-solver-round-robin-event-id.mlir",
      "layer": "l1",
      "origin": "AscendNPU-IR",
      "source_path": "bishengir/test/Dialect/HIVM/sync-solver-round-robin-event-id.mlir",
      "source_commit": "<40-hex>",
      "extraction": "verbatim",
      "features": ["sync_block", "event_id"],
      "notes": "干净文件，无需剥离"
    }
  ]
}
```

| 字段 | 约束 |
|---|---|
| `extraction` | `verbatim` / `split-input-file:<n>` / `filtered:<原因>` — 记录剥离方式，使快照可被复原验证 |
| `source_commit` | 主仓 commit 全 hash；漂移检测的锚点（D9） |
| `features` | 该语料承载的结构特征，供按需选取（如 `dynamic_shape`/`scf_while`/`preload`） |

### 14.3 准入与演进

- **准入**：新增语料的 PR 必须同时更新 manifest；缺记录即视为来源不明，`spec-gate` 拒绝（R4，随 T0.6 实现）。
- **L1 门槛**：整份语料可无 `COVERAGE_GAP` 转为 VIR，否则不得进 L1（可留在 L2 待建模补齐）。
- **不做的事**：不镜像主仓测试目录、不追求覆盖 189 个文件、不引入负例（`expected-error`）作为解析语料——负例属主仓 verifier 的职责，非本项目验证对象。
