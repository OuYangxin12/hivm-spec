# T4.0 决策：z3 依赖策略

> 决策日期：2026-09-10。所有数字为本机实测（py3.10 / linux x86_64），非估计值。

## 背景

M4 的 T4.1/T4.2 需要 SMT 求解器做有界符号等价。M4 卡 §5 风险 1 要求先评估
CI 影响，再决定 z3 是硬依赖还是可选依赖，并定下缺失时的降级口径。

## 实测数据

| 指标 | z3-solver 5.1.0 | 对照 |
|---|---|---|
| 安装体积 | **50 MB** | numpy 34 MB、ml_dtypes 24 MB、jsonschema 0.7 MB |
| `import z3` 耗时 | 0.17s | —— |
| 简单 UNSAT 查询（32 位 BitVec 交换律） | ~6ms | —— |
| 冷装耗时 | ~8s | —— |

## 决策 1：保持可选依赖（`[symbolic]` extra）

`pyproject.toml` 早在 M0 就预留了 `symbolic = ["z3-solver~=4.15"]`，本决策**确认**
该定位，不升为硬依赖。

理由**不是体积**（50 MB 与 numpy 34 MB 同量级，可接受），而是**必要性**：

- CI 的 `lint + types`、`schema roundtrip golden`、`spec-gate` 三个 job 装的是
  `.[test]`，它们完全不碰符号后端；
- `core` 矩阵 job 装 `.[test,numeric]`，测的是具体档。符号档工具有自己的测试，
  应当在装了 z3 的环境里跑，而不是让全部四个 job 都背上 50 MB。

## 决策 2：版本约束 `~=4.15` → `>=4.15`（**修正一处真实错误**）

实测发现 `~=4.15` **不允许** 5.1.0：

```python
>>> "5.1.0" in SpecifierSet("~=4.15")
False
>>> "4.16" in SpecifierSet("~=4.15")
True
```

`~=4.15` 等价于 `>=4.15, ==4.*`，把 z3 锁死在 4.x。而 PyPI 当前最新是 5.1.0，
即按现有约束 `pip install -e ".[symbolic]"` 会装到一个**过时的 4.x**，或在
4.x 已下架时直接解析失败。

这个错误此前没被发现，是因为**从来没有人真正安装过这个 extra**——它在 M0
被写下作为占位，M1–M3 都没用到。这正是"预留的依赖声明必须在首次使用时复核"
的例子。

改为 `>=4.15`：不设上界。z3 的 Python API（`Solver`/`BitVec`/`Real`/`Array`）
长期稳定，收紧上界带来的维护成本大于收益。

## 决策 3：缺失时的降级口径

**照搬 `ml_dtypes` 的既有模式**（`numeric.py`），不自创第四种：

1. 底层模块抛 `SymbolicSupportError`（对应 `NumericSupportError`）；
2. 装配层捕获，降级为 `COVERAGE_GAP` 并在 verdict 上标注环境原因；
3. CLI 层对"环境不可用"返回 `EXIT_PENDING`（3），与"验证失败"（1）区分。

**注意**：`Verdict` 是封闭枚举，**没有** `PENDING` 成员（框架 §7.3）。PENDING 是
**退出码层**的概念（`EXIT_PENDING = 3`），不是 verdict 层的。这两层不要混淆——
M4 卡 §3 T4.0 验收里写的"报 PENDING"指的是退出码语义。

绝对禁止的降级方式：

- 缺 z3 就跳过符号检查并报 OK（把"没装依赖"伪装成"验证通过"，FR6）；
- 缺 z3 就退回具体档并报 OK（两者结论强度不同，M4 卡 §4.1）。

## 对 CI 的影响

本决策**不改动 `.github/workflows/ci.yml`**。符号档测试用
`@pytest.mark.requires_z3` marker 隔离，与既有的 `requires_bindings` 同构：
缺依赖时显式 skip 并带任务号，不静默绿（AGENTS.md §5）。

若 T4.2 完成后判断符号档需要 CI 保护，再单独加一个装 `.[test,symbolic]` 的
job——那是一次独立的、可评估的变更，不应混在本决策里。
