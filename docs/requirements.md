# AI 辅助 pass 开发的快速语义验证能力 — 需求文档

> **状态**：需求讨论稿 v0.1。
> **范围声明**：本文档只包含需求、需求分解与未决问题；**不含实现方案、技术选型与架构设计**。此前调研与讨论中出现的任何机制性描述（执行、建模、工具形态等）均属候选方案，一律不在本文档中固化，留待方案讨论阶段决定。
> **输入**：HIVM 可行性调研、preload 特性开发实践经验、多轮需求收敛讨论。

## 1. 背景与问题陈述

### 1.1 工程背景

本项目在 pass 开发中采用 vibecoding 实践：AI 代理承担 pass 的编写、调整与迭代。开发主体（AI）在每次修改后需要快速判断"改动是否正确"，并在失败时依据反馈纠正方向。**验证回路的质量直接决定 AI 开发的方向正确性与收敛速度。**

### 1.2 现有验证手段与缺口

现有手段：编译构建 + lit/FileCheck 结构回归（check-mlir / check-bishengir，双架构）+ 真机 E2E（依赖硬件与 CANN 环境）。

| 编号 | 缺口 | 说明 |
|---|---|---|
| G1 | **语义缺位** | FileCheck 类验证是结构性的（IR 形态匹配），不验证计算语义；且 AI 可通过更新期望值使错误输出"合法化"——现有验证可被被验证者操纵 |
| G2 | **反馈速度** | 真机 E2E 资源稀缺、周期长，无法进入开发回路；全量 UT 为分钟级 |
| G3 | **维度缺失** | 三类高频验证目标现有手段完全无法覆盖：计算语义等效（尤其结构全新的 IR）、死锁、片上内存溢出 |

### 1.3 实证案例：preload 特性开发

preload / CV 流水类特性的开发经验实证了 G3：

1. 特性产出**结构全新的 IR**（新循环结构、新 buffer、新同步 op），不存在结构相似的可比对象，任何基于 IR 形态比对的手段均不适用；
2. 需要验证：变换后的计算语义与变换前**等效**；
3. 需要验证：多缓冲与 mmadL1 事件对（`sync_related_args` 中多对 Wait/Set）在**跨迭代时序下不死锁**；
4. 需要验证：变换后 IR 的 UB/CBUF 占用**不溢出**。

## 2. 目标与非目标

### 2.1 目标

1. 为 AI 的 pass 开发回路提供**快速、可依赖、防自欺**的语义验证能力；
2. 验证维度覆盖：计算语义等效、死锁、片上内存溢出，并可按需求扩展其他性质；
3. 验证能力可沿开发任务**按需生长**：支持新特性时的扩展成本与该特性引入的新语义面成比例，不为未到来的需求预付全部成本。

### 2.2 非目标

1. 周期精确或性能精确的硬件仿真；
2. 替代现有 lit/FileCheck 结构回归或真机 E2E 验收（三者职责互补，边界见 Q7）；
3. 对任意 IR 给出完备的形式化证明；
4. 初版即覆盖 RegBase/DPX 路径（见 Q5）。

## 4. 需求分解

### 4.1 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR1 | **语义等效验证** | 判定两份**允许结构完全不同**的 IR 计算语义是否等效；判定机制不得依赖 IR 结构相似性（锚点选择属方案层，见 Q1） |
| FR2 | **死锁检测** | 判定 IR 在 HIVM 同步语义（pipe/event/sync_block）下是否存在无法推进的执行；对"未发现死锁"的结论须附带其判定边界口径（见 Q2） |
| FR3 | **片上内存溢出检测** | 判定 IR 对地址空间（UB/CBUF 等）的占用是否可能超过硬件限制 |
| FR4 | **按需的覆盖生长** | 遇到验证能力未覆盖的 op/特性时，必须**显式、明确地报告缺口**（禁止静默跳过或给出不可信结论）；补齐缺口的成本与任务引入的新语义面成比例 |
| FR5 | **可诊断性** | 验证失败时输出可行动的诊断：定位到 op/源位置/触发用例，并说明问题类别（语义/死锁/溢出），使 AI 能据此修正开发方向 |
| FR6 | **防自欺性** | 验证结论不可通过修改期望值、参考数据或断言而改变；判定依据必须独立于被验证者可控的工件 |
| FR7 | **元可信性（区分谁出错）** | 能区分"被测 IR 有问题"与"验证机制自身不可用/出错"两类失败；对后者的处理方式不得误导开发方向 |
| FR8 | **确定性** | 相同输入与相同被测 IR，验证结论可复现 |
| FR9 | **程序化可用** | AI 可在开发回路中程序化触发验证并以结构化形式读取结论（接口形态属方案层，见 Q6） |
| FR10 | **可扩展的性质清单（候选）** | 未初始化片上内存读取、同步配对完整性、layout 合法性等候选验证维度，需求优先级待讨论（见 Q8） |

### 4.2 非功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| NFR1 | **速度** | 开发回路内的反馈时间预算（**建议值，待确认**）：典型单 kernel 检查 ≤ 30s；特性级完整验证 ≤ 10min |
| NFR2 | **正确性基线** | "基本可靠"的量化含义：**误判（把正确的改动判错）**是最高优先级压制目标且必须可甄别；漏报可接受但须可度量（见 Q3） |
| NFR3 | **无硬件依赖** | 验证回路的运行不得依赖真机或 CANN 运行时 |
| NFR4 | **增量成本** | 见 FR4；本条强调其作为长期约束：验证能力不应随方言演进而需要一次性全量重建 |
| NFR5 | **语义同步**（待讨论） | 验证所依据的 HIVM 语义与编译器/硬件语义演进保持一致的机制（见 Q11） |

### 4.3 约束

| 编号 | 约束 |
|---|---|
| C1 | HIVM 为封闭 ISA（约 122 op，与 scf/arith/memref/tensor 等社区方言深度混用）——验证覆盖空间有限且已知 |
| C2 | 动态 shape 与运行时 tiling 参数被广泛使用（约六成 HIVM 测试含动态维度）——验证须适用于运行时形状 |
| C3 | A3（membase）与 A5（regbase）双路径在 master 并存——验证需求是否分叉待讨论（Q5） |

### 4.4 验收标准（需求级）

| 编号 | 标准 |
|---|---|
| AC1 | 以 preload 类特性为案例：对**注入已知缺陷**的 IR（语义错误 / 死锁 / 溢出各一），验证能力能分别检出并给出符合 FR5 的诊断 |
| AC2 | 反馈时间满足 NFR1 预算 |
| AC3 | AI 依据失败诊断在下一轮修正方向的比率可度量且达到约定阈值（度量方法待讨论，见 Q4） |
| AC4 | 防自欺测试：篡改期望值/参考数据后，验证结论不发生改变 |

## 7. 术语表

| 术语 | 定义 |
|---|---|
| 快速失败 | 验证在开发回路时间预算内给出明确结论，失败时提供可行动的定位信息 |
| 防自欺性 | 验证结论不能被被验证者（尤其 AI）通过修改期望、参考或断言而改变 |
| 语义等效 | 两份结构不同的 IR 在约定精度口径（Q12）下计算结果一致 |
| 元可信性 | 验证机制能区分"被测对象有问题"与"验证机制自身不可用" |
| 按需生长 | 验证覆盖沿开发任务引入的新语义面增量扩展，扩展成本与任务规模成比例 |
| 误判 / 漏报 | 把正确的改动判为失败 / 把有问题的改动判为通过 |
