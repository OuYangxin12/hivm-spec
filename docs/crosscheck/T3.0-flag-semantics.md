## 1. `timeline/pair-direction`：已确证，销案

**假设内容**：set/wait 配对只按 event id，不依赖 `set_pipe`/`wait_pipe` 的方向约定。

**权威依据**（`include/bishengir/Dialect/HIVM/IR/HIVMSynchronizationOps.td:43-75`）：

```tablegen
def SetFlagOp : HIVM_SynchronizationOp<"set_flag"> {
  let arguments = (ins HIVM_PipeAttr:$set_pipe,
                       HIVM_PipeAttr:$wait_pipe,
                       OptionalAttr<HIVM_EventAttr>:$static_event_id, ...);
}
def WaitFlagOp : HIVM_SynchronizationOp<"wait_flag"> {
  let arguments = (ins HIVM_PipeAttr:$set_pipe,      // 顺序与 SetFlagOp 完全相同
                       HIVM_PipeAttr:$wait_pipe, ...);
}
```

`set_flag` 与 `wait_flag` 的参数**顺序完全一致**：都是 `[set_pipe, wait_pipe, event_id]`。
配对双方在同一 `(set_pipe, wait_pipe)` 对上，方向信息对"谁配谁"不产生歧义。

`HIVMAttrs.td:633-636` 的 `sync_event_slot` 描述进一步印证："`wait` when the macro
kernel calls wait_flag on **(set_pipe, wait_pipe)**"——同一对二元组同时用于 set 与 wait。

**判定**：我方"配对只按 event id、方向仅用于展示与泳道归属"的口径与主仓一致，
且刻意不依赖方向反而更稳健（方向写错不会导致配对错乱）。**假设销案**。

## 3. `timeline/flag-initial-state`：主仓无显式定义

**假设内容**：flag 初态 = 已装载（`INITIAL_ARM = 1`，set 视为 re-arm）。

### 3.1 已检索的位置（均未找到初态定义）

| 位置 | 结果 |
|---|---|
| `HIVMSynchronizationOps.td` / `HIVMAttrs.td` / `HIVMEnums.td` | 只定义 8 个硬件 event id（`EVENT_ID0`–`EVENT_ID7`），**无初态语义** |
| GSS `SyncSolver.cpp`（`reset()` / `resetUnitFlag()`） | 是求解器内部状态复位，非硬件 flag 初态 |
| GSS `SyncSolverCodeGen.cpp`（`insertSetFlagOp` / `insertWaitFlagOp` / `generateResultOps`） | 只有注入位置逻辑，**无 wait-before-set 合法性约束** |
| `GraphSolver.cpp` | 无 `waitBeforeSet` / `mustPrecede` 一类约束建模 |
| `ConcurrencySanitizer.cpp` | 针对 Triton mbarrier，非 HIVM flag |
| 官方文档 `docs/source/**` | 反复强调 set_flag/wait_flag 成 **pair**，未述初态 |

即：**主仓 C++ 链没有显式建模 flag 初态**——它不需要，因为它自己生成的代码从不依赖。

### 3.2 行为证据（统计口径明确，可复现）

全仓 `.mlir` 中按 `(文件, event id)` 组合统计"该 event 首次出现是 set 还是 wait"：

| 范围 | 组合数 | 首次为 set | 首次为 wait |
|---|---|---|---|
| `test/**/*.mlir`（lit 测试，剔除注释行） | 5 | 5 | **0** |
| 全仓 `**/*.mlir`（含注释内 dump） | 73 | 71 | **2** |

那 2 例 wait-first 已逐一查明，**均非反例**：

- `test/Dialect/HIVM/SyncSolver/hivm-gss-custom-macro-set-slot.mlir`
- `test/Dialect/HIVM/SyncSolver/hivm-gss-custom-macro-set-pinned-event.mlir`

两者都是 `#hivm.sync_event_slot<..., set>` 模式——**macro 内部执行 set**（IR 中不可见），
GSS 在 macro 之后注入 wait_flag。文件头注释自述："macro sets internally; GSS injects
wait_flag after the macro."。反向验证一致：仅这 2 例 `set=0, wait=1` 不配平，其余
71 例全部 `wait ≤ set`。

**这类不透明 macro 是我方的真实覆盖缺口**（见 §5）。

官方文档 `DFX.md:155-161` 的完整示例同样是 set 先于 wait：

```mlir
hivm.hir.mmadL1 ...              // 生产者
hivm.hir.set_flag[<PIPE_M>, <PIPE_FIX>, <EVENT_ID0>]
...
hivm.hir.wait_flag[<PIPE_M>, <PIPE_FIX>, <EVENT_ID0>]
hivm.hir.fixpipe ...             // 消费者
```

### 3.3 结论与残余不确定性

**可以确证的**：主仓生成的代码**从不依赖 flag 出厂已装载**——每个 event 恒先 set 后 wait。

**不能确证的**：硬件上 flag 的**物理初态**究竟是 0 还是 1。主仓源码与文档都没写，
因为它的代码生成策略让这个问题不影响正确性。要真正定这个值需要**硬件 golden**
（框架 §8.1 规定的唯一仲裁路径），本项目 NFR3 约束下不接触硬件，属离线稀疏活动。

## 4. 对我方判定的影响（实测）

把 `INITIAL_ARM` 由 1 改为 0，重跑全部 11 份 L0 语料，**只有一处变化**：

| 语料 | `INITIAL_ARM=1`（现状） | `INITIAL_ARM=0` |
|---|---|---|
| `cross_iter_event_pair.mlir` | `OK` | **`DEADLOCK`（wait-cycle）** |
| 其余 10 份 | 不变 | 不变 |

`cross_iter_event_pair.mlir` 的形态是：循环体内 `wait(EVENT_ID0)` → load →
`set(EVENT_ID0)`，且**函数第一条同步指令就是 wait**，该 event 此前无任何 set。

按 §3.2 的证据，**主仓从不生成这种形态**。所以：

- 若初态为 1：该语料健康（首个 wait 消费初始装载，此后 1:1 自续握手）；
- 若初态为 0：该语料的首个 wait 永久饿死 → 真实死锁。

同时实测确认：`wait` 先于任何 `set` 的最小形态（`/tmp/waitfirst.mlir`，1 wait + 1 set）
当前判 `OK`/exit 0。**若真实初态为 0，这是一个假阴性。**

## 5. 新发现的覆盖缺口：不透明 macro 的内部 set/wait

`CustomMacroOp` 带 `sync_event_slots` 属性时，set 或 wait 可能发生在 **macro 内部**，
IR 里看不见（§3.2 的那 2 例）。我方 timeline 引擎只统计 IR 中显式的 set/wait。

`sync_event_slot` 的三种模式（`HIVMAttrs.td:610-620`）：

| 模式 | 语义 | IR 中可见的部分 |
|---|---|---|
| `internal`（默认） | GSS 只分配 event id，不注入边界 set/wait | 无（macro 内部自成配对） |
| `wait` | macro 内部 wait；GSS 在 macro **前**注入 set | 只见 set |
| `set` | macro 内部 set；GSS 在 macro **后**注入 wait | 只见 wait |

### ⚠ 本节初稿把风险方向判反了，实测已纠正

初稿推断"低估 set 供给 → 规则 A/C **假阳性**"。实测证伪：

```
1 个孤立 wait（event 全模块无 set）  INITIAL_ARM=1 → OK          ← 规则 A 被掩盖
1 个孤立 wait（event 全模块无 set）  INITIAL_ARM=0 → DEADLOCK
2 个孤立 wait（event 全模块无 set）  INITIAL_ARM=1 → DEADLOCK
```

**根因**：规则 A 要求 `blocked_in_both`（两种贪心序下都受阻）才判定，而
`INITIAL_ARM=1` 让**第一个** wait 消费掉初始装载并成功执行，于是它不算"受阻"。
必须有**第 2 个** wait 才触发规则 A。

所以对 `macro_sync=set` 形态（IR 中恰好留下 **1 个** wait），真实风险方向是：

- **当前判 `OK`，但这是碰巧正确**——该形态下 macro 内部确有 set，本就该健康。
  问题在于结论的**理由是错的**：它凭"消费初始装载"而非"识别 macro 内部 set"
  得出 OK。
- 一旦 `INITIAL_ARM` 改为 0，同一形态立刻变成**假阳性** DEADLOCK。

即：**`INITIAL_ARM=1` 目前掩盖了这个缺口，而不是暴露它**。这也解释了为什么
L0/L1/L2 语料从未报出问题——保护来自一个不相干的假设，不是来自正确建模。

### 处置

识别 `sync_event_slots` 属性，把 `set`/`wait` 模式的槽位计入供需账目（macro 视为
该 event 的一次隐式 set 或 wait）。这样：

- 结论不再依赖 `INITIAL_ARM` 的巧合；
- `INITIAL_ARM` 未来若改为 0，不会立刻产生假阳性；
- 无法解析槽位时按 `COVERAGE_GAP` 降级，**不得**让规则 A/C 在缺口上出 DEADLOCK（NFR2）。

### 附带发现：规则 A 的 1-wait 盲区

`INITIAL_ARM=1` 下，"恰好 1 个 wait 且该 event 全模块无 set"永远判 `OK`。
这是初始装载假设的**直接代价**，此前未被任何语料或测试覆盖——既有语料
`waits_before_sets_deadlock.mlir` 用了 2 个 wait，正好跨过盲区。
