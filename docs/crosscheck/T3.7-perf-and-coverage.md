# T3.7 性能复查与等价验证覆盖面实测

> 复查日期：M3 末 ｜ 引擎：equivalence 0.1.0 ｜ 语料：L0 12 + L1 10 + L2 19 = 41 份
> 复现命令见 §5。

## 1. 结论速览

**性能远达标，覆盖面受语义边界限制。**

| 项 | 预算（D10） | 实测 | 余量 |
|---|---|---|---|
| 等价验证（具体档） | ≤ 5min / kernel 对 | **0.23s** 最大单例（总 1.22s，均 0.03s） | ~1300× |
| 特性级完整验证 | ≤ 10min | **1.16s**（41 份 × 3 工具） | ~517× |

性能不是 M3 的瓶颈，**不触发**"超限则替换执行核"的评估条款（M3 卡 §3 T3.7）。

覆盖面：41 份语料自对拍，**5 份 OK、36 份 COVERAGE_GAP**。下面逐条说明缺口
成因——其中两条是设计边界，一条是本次修掉的真实缺陷。

## 2. 缺口成因分解

### 2.1 逃生舱 op（20/41）——设计边界，不可消除

`hivm.hir.mmadL1` 是描述里唯一的逃生舱 op（OD8），理由已在描述中写明：
"MMA 值语义依赖分形布局代数（OpLayoutInterface），无法声明式表达"。

它没有可执行值语义 → 其结果不参与对拍 → **下游全部失去可比性**。L2 语料以
matmul 流水线为主，`mmadL1 → fixpipe → load → vexp` 是典型链路，一个逃生舱
op 会让整条链退化。这解释了 `fixpipe`(21)/`mmadL1`(20)/`vexp`(17)/`copy`(13)
这组高频"未建模"计数——**它们大多不是自己没建模，而是操作数来自逃生舱**。

这是**正确行为**：D9 规定未经对拍的语义不得臆造，猜一个 MMA 布局代数写进去
才是真正的风险。M4 引入 z3 后可用符号模式部分绕开（不需要具体值即可比较结构
等价），但在 M3 的具体执行档里，这条边界不可消除。

### 2.2 动态 shape 入参（20/41）——设计边界，刻意不猜

真实语料大量使用 `memref<?xf16>`。T3.4 明确规定动态维**不猜具体值**：猜 1 会
让边界语义失真，猜 256 会让预算失真，两者都会把"不知道 shape"伪装成"验证过
了"（FR6）。故这些参数不生成输入，其下游同样失去可比性。

M4 可通过符号 shape 或用户显式提供 shape 提示来缓解。

### 2.3 输入面推导错误（曾影响 37/41）——**真实缺陷，本次修复**

这是 T3.7 最有价值的产出：性能复查顺带暴露了一个我在 T3.4 埋下的设计错误。

**症状**：41 份语料里 37 份报 COVERAGE_GAP，其中大量是"操作数未绑定值"。

**根因**：T3.4 用 `VAlloc(origin=FUNC_ARG)` 作为入口输入的来源，而
`ir_engine._record_func_args` **刻意只登记带 `#hivm.address_space` 标注的
参数**——那是**占用分析**的口径（无标注的通常是 host 侧内存，不占片上空间，
算进来会造成占用假阳性）。

但等价验证要给 kernel 喂输入，需要的是**全部**函数参数。真实 L2 语料的入参
多为 `memref<16x16xf16>` 这类无标注形式，于是 `specs_from_module` 推出 **0 个
输入** → `load` 无值可用 → 雪崩成一整片缺口。

**这不是引擎 bug，是我复用了一个语义不匹配的数据源。**

**修法**（已与用户确认方案）：VIR 契约新增 `VFuncArg`，登记 kernel 的全部函数
参数；`allocs` 语义保持不变。两者刻意分开：
- 把无标注参数塞进 `allocs` → 占用分析把 host 内存算进片上预算（**假阳性**）；
- 让等价验证只看 `allocs` → 推不出输入，整份 kernel 退化（**假缺口**）。

**效果**：L2 样例的函数参数由 0 个变为 3 个（`?xi8` / `16x16xf16` / `?xf16`）。

### 2.4 一元 elementwise 不支持（曾影响 vexp/vcast）——**真实缺陷，本次修复**

`hivm.hir.vexp` 的描述写着 `elementwise(exp, src, into=out)`，却被判为"无可
执行值语义"。原因是 T3.1 的 `parse_value_kernel` 硬性要求 elementwise 至少
两个操作数——**明明描述里写了语义，却因实现只支持二元而退化成覆盖缺口**。

已补一元支持（`exp`/`neg`，双模）。可执行内核 6 → 7，OK 语料 4 → 5。
`vcast`（`elementwise(cast, src)`）是 dtype 转换而非算术，归 T3.3 的 dtype
机制，未在此处顺手实现——那需要目标 dtype 参数，属于独立设计。

### 2.5 无值语义的同步 op（set_flag / wait_flag / pipe_barrier）——正确

这些 op 本就没有值语义，其"未建模"计数是**预期的**：它们由 timeline 工具负责，
不参与数值对拍。

## 3. 修复后的覆盖面

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 可执行值内核 | 6 | **7** |
| OK 语料 | 4 | **5** |
| 因输入推导失败而缺口 | 大量 | 已消除（改为如实报告动态 shape） |

剩余 36 份缺口中，**绝大多数由 §2.1 逃生舱与 §2.2 动态 shape 两条设计边界
决定**——它们是 M3 具体执行档的固有上限，不是实现缺陷。

## 4. 对 D8"最小等价内核"的诚实评估

D8 要求的能力（具体执行差分 + 逐 op 值哈希 trace + 首发散点定位）**已全部实现
并验证有效**：在 `loop_load_add_store` 上注入 `vadd→vmul`，工具报 MISMATCH 并
定位到 `vmul@i0` 及源码行，附双侧值摘要与影响计数。

但必须说清楚：**能力可用 ≠ 全语料可用**。M3 的具体执行档目前只能完整覆盖
不含 MMA、且入参 shape 静态的 kernel。这不是"验证通过"，而是"在这 5 份语料
上验证通过，其余 36 份如实报告为未验证"。

按 D8 的措辞——范围可缩，能力不得删除或无限延期——这符合要求：能力在，范围
受语义边界限制且**已如实登记**。

## 5. 复现

```bash
cd hivm-spec
export HIVM_SPEC_BINDINGS=$PWD/.bindings
.venv310/bin/python -m hivm_spec gen specs/toy.py specs/cv.py -o build/config.json

# 单份对拍 + 注入缺陷检出
L=specs/cases/corpus/l0/loop_load_add_store.mlir
sed 's/hivm\.hir\.vadd/hivm.hir.vmul/' $L > /tmp/broken.mlir
.venv310/bin/python -m hivm_spec tool equivalence /tmp/broken.mlir \
    -c build/config.json --anchor $L --no-chart --json /tmp/eq.json
# → MISMATCH，退出码 1，首发散 vmul@i0

# 无锚点必须是缺口而非 OK
.venv310/bin/python -m hivm_spec tool equivalence $L -c build/config.json --no-chart
# → COVERAGE_GAP，退出码 4
```

全语料性能与缺口统计脚本见提交历史中的 `/tmp/t37_perf.py`、`/tmp/t37_why.py`
（临时脚本，未入库；上述数字由其产出）。
